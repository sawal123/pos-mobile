# Workflow

- Strict scope discipline: complete the assigned phase without expanding scope; don't audit/refactor unrelated areas, and don't modify production code in test-only phases. Confidence: 0.9
- If a real production bug is found during testing: first write a failing regression test, identify the exact layer, then apply the minimum fix without refactoring. Confidence: 0.8
- Git workflow: work on a dedicated branch (e.g., test/<phase>-pNN), commit, push, and open a PR to main — never self-merge; for follow-up/final-repair rounds keep the SAME branch and PR (no new branches or PRs). Confidence: 0.9
- Validation gates before finishing: run the new spec, then the previous phase's regression, then the full unit regression, then the production build — all must pass. Confidence: 0.8
- Avoid adding new dependencies, persistence keys/migrations, or DB schema changes during test/hardening phases. Confidence: 0.8
- QA/reporting honesty is non-negotiable: never claim a test/QA result that wasn't actually performed (no fabricated reports, no emulator/simulator passed off as a real device, no "tested" claims without the real hardware/toolchain); report unperformed scenarios as NOT_RUN with explicit blocker codes (e.g., REAL_ANDROID_DEVICE_REQUIRED, MACOS_XCODE_IPHONE_REQUIRED), and keep the overall phase status BELUM SELESAI while any required platform is untested. Confidence: 0.95
- Detect and record the environment (OS, Node, npm, Java, Capacitor CLI, adb, Xcode) before starting a build/QA phase; if a required tool or physical device is missing, report it as a blocker rather than assuming it exists or skipping detection. Confidence: 0.9
- Never commit build artifacts (APK/AAB/IPA/xcarchive), keystores, passwords, .env, or signing secrets to the repo; don't create dummy keystores to fake a signed release — an unsigned release build that compiles is acceptable with signing explicitly deferred. Confidence: 0.9
- Maintains structured QA documentation in the repo (e.g., docs/qa/): base commit, branch, environment versions, build results with artifact paths, per-scenario PASS/FAIL/NOT_RUN matrix, bugs found/fixes performed, remaining blockers, and final verdict. Confidence: 0.7
- QA status precision in docs: never upgrade a partially verified result to full PASS — mark it PARTIAL / PENDING <DOMAIN> VERIFICATION (e.g., PENDING CLOUD VERIFICATION) and state exactly what remains unverified; enumerate ALL scenarios in the matrix (e.g., A1–A21) with explicit PASS/PARTIAL/NOT_RUN rather than only the passing subset; use explicit fix-status tokens (e.g., FIXED_AND_DEVICE_VERIFIED) and remove superseded pending blockers; keep the phase verdict BELUM SELESAI while any scenario/platform is unverified. Confidence: 0.9
- For mobile/native QA phases, run the full validation chain before device QA: web regression + production build → cap sync → clean Android builds (assembleDebug / assembleRelease / bundleRelease) → record artifact outputs, then attempt real-device scenarios. Confidence: 0.8
- Avoid hardcoding absolute project paths in file operations/commands; use relative paths from the current repo working directory (e.g., `docs/qa/...`), even when the repo sits under a deep absolute path. Confidence: 0.9
- Manual physical-device tests are performed by the user, not the agent: once the environment is ready, stop and hand off the test with explicit report fields, never enter credentials yourself, and never mark a scenario PASS until the user reports real device results. Confidence: 0.9
- Credential/secret hygiene during QA: don't read or print passwords/tokens/secrets from .env or the database, don't auto-create test users/accounts (reuse existing dev/test accounts), and never write credentials, tokens, or device serials into commits or QA reports. Confidence: 0.9
- Mobile QA against a local backend: tunnel the device to the host via `adb reverse tcp:<port> tcp:<port>` and point the app's API base URL at localhost; pass env vars inline at build time rather than writing a .env that isn't gitignored, and avoid unnecessary rebuilds by checking whether the current build already has the right config. Confidence: 0.85
- Preserve app persistence across QA reinstalls: use `adb install -r` and never uninstall the app so local data (e.g., SQLite) survives. Confidence: 0.85
- Pulling a debug app's SQLite DB from an Android device for inspection: use `adb exec-out run-as <pkg> cat databases/<file>` (run-as blocks writing to /data/local/tmp), then query with the sqlite3.exe from the Android SDK platform-tools; inspect only non-sensitive metadata keys, never tokens/passwords. Confidence: 0.8
