# Testing

- Integration/hardening tests must use real services, stores, queue, mapper, and adapters; mock only the network transport / fake server. Confidence: 0.9
- Bans fixed timers (setTimeout, setInterval, sleep) in sync tests; use deferred promises and awaited hooks for deterministic control. Confidence: 0.9
- Tests must be independent and deterministic: no it.skip/.only, no reliance on Vitest execution order, and always cleanup (dispose trackers, stop listeners, close schedulers) so no async leaks. Confidence: 0.8
- Restart/lifecycle tests must simulate a genuinely fresh app graph (new Pinia, new sync foundation, new stores/services); never reuse old in-memory app objects — only durable state (adapter/database, fake server) survives. Confidence: 0.8
- Treat existing production code and prior tests as the contract: don't invent semantics (e.g., no fake durable checkpoints that production never writes), assert according to real production ordering (e.g., cursor saved last), reuse existing helpers, and keep test-only capabilities within valid production contracts (e.g., server returning a smaller page with has_more=true). Confidence: 0.85
- Inject failures at the real production boundary — e.g., a fail-once wrapper over an adapter/service method that throws once then delegates to the original — never by manually rewriting durable state (fake cursor checkpoints) or fixed timers. Confidence: 0.9
- Prove idempotency and negative claims (no reapply, zero extra HTTP, same request_id) with server-side evidence: request logs, server sequence counters, and request counts — not only client-side end state. Confidence: 0.8
- Prefers exact assertions over fallback arrays: pin error codes/statuses to the current real production contract with exact `toBe` single values (e.g., `code === 'SYNC_CONTEXT_GUARD_BLOCKED'` plus `contextGuardCode === 'SYNC_CONTEXT_BUSINESS_MISMATCH'`) — never accept permissive fallback lists (`toContain([...])` of several possible codes). Confidence: 0.9
- Prefers exact assertions over fallback arrays: assert error codes/statuses with exact `toBe` single values (e.g., `code === 'SYNC_CONTEXT_GUARD_BLOCKED'` + `contextGuardCode`) and pin assertions to the current real production contract — never accept permissive fallback lists (`toContain([...])` of multiple possible codes). Confidence: 0.9
- Android crash triage: don't treat Xiaomi/Qualcomm/System log noise as app crashes; declare a native crash only when evidence points to the app's own process (e.g., `Process: <app-package>` or a FATAL EXCEPTION for that package). Confidence: 0.9
- Before declaring a bug from a device-QA report, verify the scenario was actually executed: confirm its prerequisite scenario passed (e.g., A11 only valid after A10 PASS), inspect what was really persisted on the device (pull the app SQLite / secure storage), and ask the user a structured clarifying question about the exact steps performed — a result reported for a scenario that wasn't truly run is invalid evidence, not a bug. Confidence: 0.85
